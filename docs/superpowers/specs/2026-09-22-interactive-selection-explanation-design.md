# Daily Translate 划词交互式解读设计

## 1. 背景与目标

现有划词翻译和划词解读都在选中文字后立即调用模型。划词解读只能展示一次回答，用户无法针对术语、逻辑、背景或模型回答继续追问；用户只是复制文字时也可能误触发请求。

本次目标是把两个划词模式合并为“划词工具”：选中文字后先显示操作条，用户明确点击“翻译”或“解读”才调用模型；解读使用临时对话框，允许围绕当前选区继续追问。

第一版以最小可用范围为准：

- 会话只存在于当前页面内存中。
- 关闭对话框、刷新、跳转或重新选择文字后结束会话。
- 不保存、不恢复、不管理历史会话。
- 不增加服务端、中转服务或新的用户配置项。
- 整页翻译的数据流和串行处理行为保持不变。

## 2. 方案选择

### 2.1 采用方案：页面持有临时会话，每轮建立独立请求

Content Script 保存当前选区、页面上下文和可见的用户/助手消息。首次解读及每次追问都建立一个新的 `translation` Port，把截至当前轮的完整会话发送给 Service Worker。请求完成或失败后断开该 Port。

该方案复用现有取消、监控、日志和 pi 适配入口，不依赖 Service Worker 在两轮对话之间持续存活，也不引入持久化状态。

### 2.2 不采用的方案

- 长连接持有会话：依赖 MV3 Service Worker 生命周期，页面和后台之间还要同步会话状态，复杂度高于第一版需要。
- `chrome.storage` 持久化会话：可以支持刷新恢复，但需要会话索引、清理、容量和隐私设计，本次不实现。
- 只把历史拼成一个长字符串：实现简单，但会丢失用户和助手角色语义。第一版使用 pi 的多消息上下文。

## 3. 用户交互

### 3.1 划词操作条

插件开启且当前页面模式为“划词工具”时，用户用鼠标左键选择包含文字的内容，选区附近显示操作条：

```text
┌─────────────────┐
│  翻译  │  解读  │
└─────────────────┘
```

- 显示操作条时不调用模型，不消耗 Token。
- 点击“翻译”关闭操作条并沿用现有单次翻译浮层。
- 点击“解读”关闭操作条、创建临时会话、打开对话框并自动发起首次解读。
- 点击操作条和选区以外的区域关闭操作条。
- 纯数字、标点、空白和 Emoji 不显示操作条。
- 插件关闭或当前页面处于“整页翻译”模式时不显示操作条。

### 3.2 解读对话框

```text
┌──────────────────────────────────┐
│ AI 解读        已选内容摘要   × │
├──────────────────────────────────┤
│ AI                               │
│ 首次解读内容……                   │
│                                  │
│                         用户问题 │
│                               …… │
│                                  │
│ AI                               │
│ 后续回答……                       │
├──────────────────────────────────┤
│ 继续追问…                  发送  │
└──────────────────────────────────┘
```

- 对话框仍使用封闭 Shadow DOM，避免页面样式污染。
- 桌面端宽度沿用紧凑悬浮面板风格，但增加可滚动消息区和输入区；尺寸不得超过当前视口。
- 标题区显示“AI 解读”和截断后的已选内容，完整原文不额外复制到消息区。
- 模型回答和用户问题按时间顺序展示；所有内容使用 `textContent`，不解析 Markdown 或 HTML。
- `Enter` 发送，`Shift+Enter` 换行；空白问题不能发送。
- 同一时间只允许一个请求。请求中禁用输入与发送按钮，并显示正在回答状态。
- 关闭按钮和 `Escape` 关闭对话框、取消在途请求并销毁会话。点击网页其他区域不关闭已经打开的对话框，避免用户阅读或复制页面内容时误关。
- 用户在对话框外重新选择文字时，先结束旧会话，再为新选区显示操作条。

### 3.3 失败与重试

- 首次解读失败时，对话框保留选区信息并在助手位置显示错误和“重试”操作。
- 追问失败时，不把失败的用户问题加入已完成会话；输入框保留该问题，并显示本轮错误，用户可直接重试。
- 重试仍是一次新的模型请求，照常统计 Token、延迟和日志。
- 输出达到长度限制时，如果实时显示已开启且已经收到部分内容，则保留该内容并标记回答不完整；该回答不加入后续会话，必须重试或改写问题。

## 4. 模式调整与兼容

控制面板的页面模式由三项收敛为两项：

```text
划词工具
整页翻译
```

- 内部继续使用 `selection` 表示“划词工具”，避免无意义地重命名消息字段和状态变量。
- 移除控制面板中的 `explain` 选项。
- Content Script、Popup 和 Service Worker 读取到已有 `explain` 页面状态时，将其归一化为 `selection`。
- 新页面仍默认使用 `selection`。
- `page` 的启停、活动标签页限制、失败暂停和原文恢复行为不变。

这是一次交互变化：选择文字不再自动翻译，必须在操作条明确选择动作。

## 5. 会话模型

Content Script 仅维护一个当前会话：

```js
{
  sourceText: "用户选中的文字",
  pageTitle: "最多 200 字符",
  surroundingText: "选区附近最多 1200 字符",
  messages: [
    { role: "user", content: "结构化的首次解读输入" },
    { role: "assistant", content: "首次解读" },
    { role: "user", content: "后续问题" },
    { role: "assistant", content: "后续回答" }
  ]
}
```

首次用户消息包含选中文字、页面标题和邻近上下文。后续用户消息只包含追问文本；系统提示词持续要求模型围绕原始选区和已有对话回答，不执行选区、页面上下文或历史消息中包含的指令。

第一版只把可见文本作为历史，不保留或回传模型 thinking 内容。历史助手消息转换为 pi `AssistantMessage` 时使用当前 provider、API、model 和零 usage 元数据；实际 Token 统计只使用每次新请求返回的 usage。

为防止页面异常消息制造无限上下文，Service Worker 在请求边界校验：

- 消息必须按 `user`、`assistant` 交替，最后一条必须是 `user`。
- 单条消息最多 12000 字符，会话可见文本合计最多 50000 字符。
- 角色、结构、数量或长度不合法时拒绝请求，不调用模型。

达到字符上限后，对话框提示需要重新选择文字开始新会话，不再允许继续发送当前历史。

## 6. 请求与数据流

```text
选中文字
   |
   v
Content Script 显示操作条（不请求 API）
   |                         |
   | 翻译                    | 解读
   v                         v
现有单次翻译浮层       创建页面内临时会话
                             |
                             v
                     打开独立 Port 发起本轮
                             |
                             v
Service Worker 校验会话 -> 读取模型设置 -> 构造 system prompt
                             |
                             v
pi-adapter 将规范化消息转换为 pi Context.messages
                             |
                             v
模型事件 -> chunk / done / error -> 当前助手消息
                             |
                             v
                    用户输入下一轮问题
```

### 6.1 Content Script 到 Service Worker

新增对话请求类型，不复用语义已经过载的单文本 `translate` 消息：

```js
{
  type: "explain-conversation",
  messages: [
    { role: "user", content: "..." },
    { role: "assistant", content: "..." },
    { role: "user", content: "..." }
  ]
}
```

单次翻译和整页翻译仍使用现有消息类型。每轮对话建立独立 Port，因此当前“一条 Port 只处理一个请求”的状态机无需改成多请求协议。

### 6.2 Service Worker 到 pi 适配层

`requestTranslation` 增加可选的规范化消息输入；单次翻译和整页翻译仍构造一个 user message。`pi-adapter` 接收完整消息数组并生成 pi `Context.messages`：

- user 消息映射为 pi `UserMessage`。
- assistant 消息映射为只含 text block 的 pi `AssistantMessage`。
- system prompt 仍单独传递，不放入历史数组。
- adapter 继续统一处理 provider、model、取消、超时、事件流、usage 和错误。

每轮回答沿用 30 秒活动超时。收到 text 或 thinking 事件时刷新计时；thinking 不展示、不记录，也不作为 TTFT。

## 7. 状态与取消

Content Script 分别持有操作条状态、单次翻译状态和对话状态，但任一时刻只有一个划词交互处于活动状态：

- 新选区出现：取消单次翻译或对话请求，销毁旧浮层/会话，显示新操作条。
- 点击翻译：销毁操作条，创建单次翻译请求。
- 点击解读：销毁操作条，创建对话会话和首次请求。
- 关闭对话框、按 `Escape`、关闭插件、切换为整页模式、页面卸载：断开 Port 并清空会话。
- 请求序号继续用于忽略旧请求的迟到消息，防止旧回答写入新会话。

对话框关闭后不提供恢复入口。刷新和跳转自然销毁 Content Script 内存，符合第一版生命周期。

## 8. 监控、日志与隐私

- 首次解读和每次追问分别计为一次模型请求，分别记录 Token、TTFB、TTFT、完成耗时、成功、失败、超时或取消。
- 后续请求会重复发送本次对话历史，因此输入 Token 会随轮数增长；README 必须明确说明。
- 成功日志文案从仅指向翻译的表述调整为通用“模型请求成功”；错误日志沿用现有详细错误结构。
- 不把选中文字、页面上下文、问题、回答或 thinking 写入 `chrome.storage`、运行日志或网页自身的 light DOM。
- Content Script 的 Shadow DOM 和内存中会短暂存在可见会话文本；关闭、刷新或跳转后释放。
- 所有请求仍直接发送到用户配置的模型服务，不经过 Daily Translate 服务器。

## 9. 文件与职责

- `content/content-script.js`
  - 选区操作条、对话框、输入交互、临时会话、每轮 Port 和取消状态。
  - 复用现有选区定位、上下文提取、Shadow DOM 样式和错误展示原则。
- `background/service-worker.js`
  - 新消息类型、会话校验、对话提示词、请求监控和错误映射。
- `background/pi-adapter.js`
  - 把规范化的多轮消息转换为 pi `Context.messages`。
- `popup/popup.html`、`popup/popup.js`
  - 模式列表合并和已有 `explain` 状态归一化。
- `README.md`
  - 新交互、会话生命周期、隐私范围和重复历史带来的 Token 消耗。

第一版不拆分新的前端模块。现有 Content Script 较大，但本次逻辑与选区浮层共享大量状态和生命周期；为了单一功能提前引入模块构建边界会扩大改动范围。

## 10. 验证标准

实现完成后执行现有静态和构建检查，不新增单元测试：

1. 所有 JavaScript 文件通过 `node --check`。
2. `npm run build` 成功，构建后的 Service Worker 不含动态 `import()`。
3. Manifest JSON 和 `git diff --check` 通过。

在 Chrome 普通 HTTP/HTTPS 页面手工验证：

1. 选择文字只显示操作条，监控数据不增加；点击翻译后只产生一次请求。
2. 点击解读自动得到首次回答，追问能引用此前选区和回答。
3. 实时显示开启时当前助手消息逐步更新，关闭时只在完成后显示。
4. 请求期间不能重复发送；关闭、新选区、停用插件和切换整页模式会取消请求且不串写旧结果。
5. 刷新、跳转和关闭对话框后旧会话不可恢复。
6. 首次或追问失败时可以重试，失败轮次不会污染后续历史。
7. 达到消息或字符上限后不再调用模型，并显示明确提示。
8. 现有 `explain` 页面状态升级后归一化为“划词工具”，整页翻译行为不变。
9. Token、延迟和日志按每轮请求各记录一次，存储中不出现会话正文。

## 11. 不在本次范围内

- 刷新、跳转、重新打开页面后的会话恢复。
- 关闭对话框后恢复会话。
- 多会话列表、对话历史、搜索、导出或同步。
- 编辑、删除、重新生成某条已完成消息。
- Markdown、代码高亮、图片、文件、网页全文问答或工具调用。
- 自动总结或裁剪超长历史。
- 每个模式单独配置模型或提示词。
